# AEVORA V12 — Testing & Acceptance

## Acceptance principle
A feature is not accepted because it looks correct. It is accepted only when the visual result can be traced to authoritative Aevora state and authorized actions.

## Required verification
- no duplicate enterprise systems
- identity mapping
- company isolation
- real company/building visualization
- departments/employees/leadership
- real vehicles/travel
- persistent operation while Chairman is elsewhere
- realtime events
- voice/controller interaction
- VR without keyboard
- meetings and executive commands
- unauthorized-action rejection
- failure/recovery/reconciliation
- streaming/performance
- security
- V1–V11 regression

## End-to-end invariant
Aevora truth → world state → simulation → rendering → interaction → authorization → Aevora state change → world update.

## Engine POC
The final 3D engine must be selected through evidence covering digital humans, buildings, vehicles, geography, VR, performance, streaming, tooling, integration and maintainability.
